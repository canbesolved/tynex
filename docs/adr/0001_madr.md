# Record decisions with MADR

## Context and Problem Statement

`tynex` is built by a human maintainer and AI agents. Design decisions
must survive between sessions and contributors, with the reasons
behind them, not only the result.

## Decision Drivers

- Decisions must be easy to find, read and supersede.
- Plain Markdown in the repository, reviewed with the code.
- Light tooling, no server or web UI.

## Considered Options

- MADR 4.0 records in `docs/adr/`, `adr-log` for the index
- Nygard format with `adr-tools`
- `log4brains`
- Decisions only inside architecture pages

## Decision Outcome

Chosen option: "MADR 4.0 records in `docs/adr/`, `adr-log` for the
index", because MADR captures options and trade-offs explicitly and
`adr-log` is the index tool from the MADR authors.

### Consequences

- Good, because every decision has context, options and consequences.
- Good, because `scripts/new_adr.sh` and `scripts/adr_log.sh` make it
  one command to add a record and refresh `docs/adr/index.md`.
- Bad, because `adr-log` needs Node.js (already used for
  `markdownlint-cli2`).

### Confirmation

Code review: a change that makes a significant design choice comes with
a new or superseding ADR.

## More Information

- Files: `NNNN_short_slug.md`, underscores per project naming rules.
- Template: [adr_template.md](adr_template.md), MADR 4.0.0.
- A changed decision gets a new ADR; the old one is set to
  `superseded by ADR-NNNN`.
